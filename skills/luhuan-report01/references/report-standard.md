## 1. 核心原则

- 先给决策结论，再解释过程。
- 评测“当前能复现的公开能力”，不要用愿景替代产品现状。
- 将模型能力、工程能力、产品能力、数据壁垒和商业价值分开。
- 将视觉效果、三维几何、物理可用性和行业交付级精度分开。
- 每个重要结论同时给出证据类型、边界和下一步验证方式。
- 保留失败样本。失败比精选 Demo 更能说明产品化成本。

## 2. 标准十四章

封面不是编号章节，必须包含：项目名、报告副标题、版本、日期、证据截止日期、研究对象、关联平台、证据范围、报告性质，以及一条不超过 90 个汉字的“一句话判断”。

### 01 先给结论

回答是否值得继续、价值不在哪里、真正值得验证的命题。提供三至四张结论卡，建议采用：

- 技术本质
- 核心能力
- 业务价值
- 战略定位

随后给出推荐命题，避免以“更好看”“更智能”等不可测表述收尾。

### 02 公开/开源内容盘点

列出仓库、模块、依赖模型、权重、许可证、运行入口、输出格式和官方 Demo。用流程图展示输入到输出链路。明确哪些属于项目原创、第三方依赖、配置/胶水代码和未公开能力。

### 03 工程化还是新模型

用对照表回答：新架构、训练方法、自有权重、独立评测、工程编排、产品界面是否存在。结论允许是“混合形态”，但必须说明主导价值来自哪里。

### 04 真正解决与不能解决的问题

采用两栏或四象限：

- 能稳定解决
- 有条件解决
- 当前不能解决
- 容易被误解为能解决

至少覆盖输入限制、精度、遮挡/透明/反射、尺度、语义、编辑、实时性和下游兼容。

### 05 本地或云端案例实测

展示原始输入、阶段结果、最终结果、交互/碰撞结果、失败结果和性能摘要。禁止只放成功截图。正文需明确“这组结果证明了什么”和“没有证明什么”。

### 06 目标行业价值

将技术能力映射到实际任务，而不是泛泛列行业。室内设计默认检查：对象化、布局编辑、碰撞/稳定性检查、真实 SKU 替换、方案沟通、报价/采购映射、施工与规范校核。

对每项标注：现在可用、需要数据补全、需要人工复核、暂不可用。

### 07 Physical AI 定位

判断项目处于：内容生成、世界初始化、感知、状态估计、规划、仿真、控制、执行、反馈学习中的哪一层。写明它是完整闭环、关键组件还是准备层。

### 08 暗壳 AI 基础

使用 `ark-ai-context.md`，说明暗壳已有 Agent、设计工作流、协作反馈、行业数据与资产连接能力。所有可能变化的公司事实在报告生成时重新核验。

### 09 传统业务数据

采用三段数据流：

```text
可用数据输入 → 联合能力层 → 业务输出
```

区分已公开确认、内部待盘点和合作后才能产生的数据。至少讨论数据授权、脱敏、版本、质量和反馈闭环。

### 10 合作方式与双向价值

明确“项目给暗壳什么”和“暗壳给项目什么”。提出三至四个联合产品，但标出首个最小可验证产品。优先选择能在 4–8 周内量化验证、不会依赖大规模平台整合的命题。

### 11 验证路线图

至少分为：基准/POC、内部试用、资产/数据产品化、客户验证、长期平台化。每一阶段写：周期、输入、输出、负责人、成本级别、成功闸门和停止条件。

### 12 风险与边界

至少覆盖：技术不确定性、尺度/物理参数、第三方许可证、数据版权与隐私、质量责任、安全、外部依赖、供应商绑定和商业假设。

### 13 最终建议

固定使用三栏：

- 现在做
- 验证后做
- 暂不承诺

结论应能直接复制给管理层，并给出下一次决策所需的最小证据。

### 14 资料来源与方法

列出主要来源、发布日期/访问日期、来源类型、支持的主张。说明测试环境、方法、限制和报告不承担的责任。

## 3. 证据与引用

### 证据优先级

1. 本地可复现实测与原始日志
2. 官方代码、模型卡、论文、规范、公告
3. 权威第三方研究或披露
4. 媒体与访谈
5. 社区内容与营销材料

低等级证据可以帮助形成问题，不能单独支撑高风险结论。

### 证据账本字段

每条关键证据至少记录：

```text
evidence_id
claim
evidence_type
source_title
source_url_or_local_path
published_or_tested_at
accessed_at
supports
limitations
confidence
```

引用链接应指向支持该主张的直接页面，不链接搜索结果。少量引用原文，主要使用转述。

## 4. 技术分类

分别给出五项结论：

- 研究/模型创新
- 工程系统集成
- 数据资产
- 产品工作流
- 商业交付成熟度

### 新模型最低证据

- 可识别的新架构或训练方法
- 对应训练或微调权重
- 数据/训练说明
- 与基线对照的评测
- 代码或足够细节可供复现

不满足时使用“工程管线”“模型编排”“产品封装”或“未公开自研能力”，不要用“新模型”代称。

## 5. 部署与实测

### 环境记录

记录操作系统、GPU、显存、驱动、CUDA、Python/Node、关键包版本、磁盘用量、权重来源、许可证与登录门槛。

### 通用测试矩阵

| 维度 | 必测内容 | 证据 |
|---|---|---|
| 安装 | 冷启动、依赖冲突、权重下载 | 命令、日志、耗时 |
| 输入 | 支持格式、尺寸、边界条件 | 输入文件与参数 |
| 结果 | 成功率、质量、稳定性 | 原图、输出、失败图 |
| 性能 | 总耗时、峰值显存、磁盘 | 监控记录 |
| 可用性 | UI、批处理、错误提示 | 操作录像/截图 |
| 互操作 | 导出、回读、标准格式 | 回读日志与预览 |
| 合规 | 许可证、权重条款、数据权限 | 来源链接与审查项 |

### 3D/Physical AI 附加测试

- 分割：关键对象召回、粘连、漏分、透明/细杆/遮挡对象。
- 重建：完整性、纹理、不可见面、拓扑、部件结构。
- 场景：相机、尺度、地面、姿态、对象间关系。
- 碰撞：碰撞体数量、贴合度、穿透、过度包围。
- 动力学：落地、倾倒、支撑、堆叠、重力方向和稳定性。
- 交互：选取、拖拽、碰撞响应、重置、状态反馈。
- 导出：GLB/OpenUSD/其他格式、材质、语义、碰撞体和回读。

原始物理结果与为了演示而固定、钉扎或调参后的结果必须分开展示。

## 6. 评分卡

采用 1–5 分，同时给出置信度（低/中/高）和证据类型：

| 指标 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 可复现性 | 无法运行 | 有条件运行 | 文档完整且稳定复现 |
| 技术原创性 | 纯封装 | 有关键改进 | 新方法、权重和评测充分 |
| 输出质量 | 仅精选 Demo | 常见场景可用 | 多样场景稳定高质量 |
| 可编辑性 | 扁平结果 | 对象级但需修正 | 结构、语义、版本完整 |
| 物理有效性 | 无物理 | 粗碰撞/默认参数 | 经标定并通过基准 |
| 集成成本 | 高且脆弱 | 可封装 | API/格式/运维成熟 |
| 数据协同 | 无明确路径 | 有待验证映射 | 可形成持续闭环 |
| 商业价值 | 场景模糊 | 有 POC 命题 | 可量化并已验证 |
| 合规风险 | 不清楚 | 可审查 | 权利与责任清晰 |

总分只用于比较，不替代分项解释。对关键短板设置一票否决项。

## 7. Physical AI 判断

完整闭环通常需要：真实/模拟世界感知 → 状态表示 → 目标与规划 → 物理预测/仿真 → 控制执行 → 反馈学习。

仅生成 3D、场景图、碰撞体或仿真初始状态时，描述为“Physical AI 的世界初始化/场景编译/仿真准备层”。只有系统真实覆盖规划、控制、执行和反馈时，才称为完整 Physical AI 系统。

## 8. 合作与数据价值

合作分析必须回答：能力互补、数据互补、产品入口、反馈闭环、商业路径、权利归属、集成成本和退出机制。

数据价值按以下层级展开：

```text
原始项目文件
→ 对象/材料/尺寸/风格/动线等结构化标签
→ 规则、场景本体、SKU 和评测集
→ 训练/检索/校核/推荐能力
→ 用户反馈与项目结果
→ 可持续改进的数据闭环
```

不得假设暗壳拥有尚未公开或未经内部确认的数据字段。

## 9. HTML 视觉标准

### 信息层级

- 顶部：品牌、版本、打印和复制结论。
- Hero：标题、副标题、元信息。
- Verdict band：一句话判断，视觉优先级仅次于标题。
- 桌面端：左侧固定目录，右侧正文；移动端改为单列。
- 每章：编号、标题、导语、证据内容、结论/提醒。
- 尾部：来源、方法、版本和对外使用限制。

### 视觉语言

- 编辑部式技术报告，不做营销落地页。
- 背景使用暖灰纸张色，正文使用深墨色，蓝色用于操作和链接。
- 绿色表示已验证/可行，琥珀表示条件成立，珊瑚色表示风险。
- 使用系统字体：Inter、SF Pro、PingFang SC、Microsoft YaHei。
- 正文最大宽度约 1260px，圆角 12–18px，阴影克制。
- 图片必须带标题、说明、来源/测试状态；不使用无信息价值的装饰图。
- 证据徽章在全篇保持一致，不通过颜色单独传递含义。

### 响应式与可访问性

- 至少验证 1440px 桌面端与 390px 移动端。
- 不出现横向滚动；表格可在自身容器内滚动。
- 图片有 `alt`，链接和按钮有可辨识名称。
- 保持足够对比度，支持键盘操作和 `prefers-reduced-motion`。
- 提供打印样式，避免关键卡片跨页断裂。

## 10. 输出、数据库与外发

### 报告清单

`report-manifest.json` 至少包含：

```json
{
  "report_id": "project-slug-YYYYMMDD",
  "title": "项目评测报告",
  "project": "Project Name",
  "version": "2607.x",
  "evidence_cutoff": "YYYY-MM-DD",
  "classification": "engineering-pipeline",
  "verdict": "一句话判断",
  "ark_relevance": "high|medium|low|none",
  "status": "draft|validated|published|archived",
  "entry_url": null,
  "artifact_url": null,
  "sha256": null,
  "visibility": "internal|restricted|public",
  "expires_at": null
}
```

数据库保存清单、状态、URL、权限和哈希；HTML、图片、视频和 3D 资产放对象存储或静态站点。

### 发布选择

- 飞书内部轻量报告：生成单文件 HTML 并上传云空间。
- 邮件/离线：单文件 HTML + ZIP，可附 PDF。
- 强交互 3D/WebGL/WASM：部署完整站点到 HTTPS，飞书中使用链接预览。
- 需要 API、登录、数据库或实时数据：正式前后端部署；不得把密钥写入 HTML。

## 11. 交付验收

### 内容

- 一句话判断与最终建议一致。
- 所有高风险主张可追溯。
- 事实、实测、推断和建议未混淆。
- 正面结果与失败边界均有展示。
- 暗壳价值不是通用套话，而是映射到具体能力、数据和业务流程。

### 技术

- 本地页面返回成功。
- 所有图片 `naturalWidth > 0`。
- 控制台无错误。
- 目录、复制、打印和主要交互可用。
- 外部链接有效并使用安全属性。

### 视觉

- 桌面和移动端无横向溢出。
- 关键结论在首屏或紧邻首屏出现。
- 表格、时间线、风险卡和图片说明易读。
- 打印预览没有严重截断。

### 外发

- 删除本机绝对路径、登录指令、密码、Token、客户个人信息。
- 确认图片、项目数据、代码和模型许可证允许对应范围的分享。
- 写明版本、证据截止日期和访问权限。
